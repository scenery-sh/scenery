# Framework Handoff For Running Development Runtimes

This ExecPlan is a living document. Keep Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective current while the work runs. It
follows [PLANS.md](../../PLANS.md).

## Purpose / Big Picture

An application selects its Scenery version (the **framework**) in its root
`go.mod`: a pinned `scenery.sh` requirement, or a local replacement that
`scenery framework use --source` points at an app-local immutable snapshot under
`.scenery/framework/source/<digest>`. `scenery framework use` builds the
matching CLI (the **producer**) under `.scenery/framework/bin/` and records it in
`.scenery/build/framework.json`; launchers such as ONLV's `scripts/scenery` then
run `scenery up` through that executable.

Before this plan, a running `scenery up` never changed producers. When the app's
`go.mod` moved to another framework (for example after merging a branch that
bumped the pin), the supervisor's next build failed its framework verification
with "application framework … does not match this Scenery CLI's source …; keep
the current runtime, run scenery framework use, then restart", and kept serving
the old build indefinitely. On 2026-09-23 three ONLV checkouts were in exactly
that state; ONLV's bottom panel, generated by the new producer, then failed with
`development runtime status undefined does not match this client`, hiding the
real cause, because the old runtime's `/runtime` status had a different shape.

After this plan:

- A running `scenery up` that was started by a prepared framework executable of
  its own app root notices, before each build, that the app now selects another
  framework. It prepares that framework (exactly what `scenery framework use`
  does, including the module download) while the old runtime keeps serving, then
  stops its runtime the same way Ctrl+C does and continues as the new producer:
  the foreground process `exec`s the new executable with the same arguments, so
  the terminal, PID and output stream stay attached; a detached runtime is
  relaunched as a new detached runtime of the new producer. If preparation fails,
  or it would have to rewrite `go.mod`, the old runtime keeps serving and the
  existing framework mismatch remains the reported build error.
- The generated `dev-runtime.ts` client explains a status mismatch in terms of
  the likely cause: a runtime that does not serve `scenery.dev-runtime.status`
  at all (an older Scenery) needs `scenery up` restarted, and a revision
  mismatch names both revisions and both remedies.

Observable result: with `scenery up -o jsonl` running on a fixture app whose
`go.mod` selects framework snapshot A, running `scenery framework use --source`
for a different checkout B makes the same process emit A's terminal summary with
`"handoff"` data, then B's stream, and `/runtime` `status` answers from B
without the operator restarting anything.

## Surprises & Discoveries

- The old runtime had detected the pin change (evidence: `status` over
  `ws://localhost:4920/runtime` returned
  `compileError: "application framework sha256:9497… does not match this Scenery
  CLI's source sha256:7a7c…; keep the current runtime, run scenery framework
  use, then restart with its reported executable"`). Only the operator did not
  see it, because the newer panel rejected the status shape first.
- `RebuildAndRestart` reloads `.scenery.json` with the running producer's strict
  decoder before framework verification. A pin bump that also changes the
  configuration language would therefore surface as a config error, never as a
  framework mismatch. Detection must not depend on build error ordering.
- The first `FrameworkSnapshotDigest` compared an `EvalSymlinks`-canonical app
  root with an uncanonicalized snapshot path when the snapshot did not exist yet
  (macOS `/var` → `/private/var`), so a new selection was not recognized
  (`TestFrameworkSelectionDiffersWithoutReadingSource` "other snapshot" failed).
  `canonicalPath` now resolves the longest existing prefix.
- The `native` fixture client has no `dev_runtime` target; only the `house`
  client carries `dev-runtime.ts`. Both regenerations still ran.
- (2026-09-24 review) The early return for an unchanged selection never cleared
  the remembered failure, so after switching back to the running producer the
  repaired failed selection was skipped for the supervisor's lifetime.

## Decision Log

- Decision: hand off automatically instead of only reporting a restart
  requirement. Rationale: every Scenery bump otherwise strands each running
  worktree on the old producer until someone notices; the developer chose
  automatic handoff. Date/Author: 2026-09-23, developer.
- Decision: detect by comparing the authored `go.mod` selection with the
  running producer (pinned version string, or the digest named by an app-local
  snapshot directory), before every build, instead of classifying build errors.
  Rationale: it is a cheap parse with no hashing and it runs before the strict
  config reload that a new configuration language would break. Date/Author:
  2026-09-23, Claude.
- Decision: only producers that are a prepared framework executable of the same
  app root (`<root>/.scenery/framework/bin/…`) hand off. Rationale: repository
  harness binaries and other explicitly chosen executables are deliberate
  choices; replacing them silently would surprise Scenery developers.
  Date/Author: 2026-09-23, Claude.
- Decision: never rewrite `go.mod` during a handoff. A local replacement that
  points outside the app-local snapshot store still needs an explicit
  `scenery framework use`, which the existing mismatch error already names.
  Rationale: automatic runtime behavior must not edit authored, tracked files.
  Date/Author: 2026-09-23, Claude.
- Decision: the handoff is a full stop and start (the same shutdown as Ctrl+C,
  then startup by the new producer), not a live transfer of state. Rationale:
  retained state compatibility, ownership records and locks are already proven
  for a manual restart; a handoff must not invent a cross-specification decoder.
  Date/Author: 2026-09-23, Claude.
- Decision: each producer's `-o jsonl` stream stays self-contained. The old
  producer ends its stream with its terminal `summary` (`ok: true`, `handoff`
  data); the new producer starts a new stream (sequence 1) on the same output.
  Rationale: lines already carry their producer and schema identity, and a
  sequence cannot be continued across specifications without a private
  cross-producer protocol. Date/Author: 2026-09-23, Claude.
- Decision: a detached supervisor relaunches by `exec`ing `<new> up --detach
  -o json` (launcher mode, without the child marker), whose result lands in the
  retiring log. Rationale: a launcher cannot strictly decode a newer producer's
  session records, so waiting for the new runtime belongs to the new producer's
  own launcher. Date/Author: 2026-09-23, Claude.
- Decision: instead of a handoff result over the detached startup pipe, every
  foreground or launcher `scenery up` checks the selection before acquiring
  anything and simply `exec`s the prepared producer; the watch loop checks only
  after the initial build, which a detached child reaches only after readiness.
  Rationale: this removes a private cross-process protocol; the only remaining
  pre-readiness case is a `go.mod` edit during detached startup, where the
  child's initial build fails with the existing framework mismatch and a rerun
  hands off at startup. Date/Author: 2026-09-23, Claude.
- Decision: a failed preparation is not retried for the same desired selection
  until `go.mod` selects something else. Rationale: an offline download or a
  broken producer build would otherwise repeat on every save. The rebuild error
  names the manual path. Date/Author: 2026-09-23, Claude.
- Decision: that suppression lasts one selection episode: selecting the running
  producer again, or an unreadable selection, forgets the failure. Rationale:
  reselecting the framework is the developer's retry, while saves that keep the
  failed selection still do not retry. Date/Author: 2026-09-24, Claude.

## Context and Orientation

Framework selection lives in `internal/build`:

- `framework_session.go`: `ResolveFrameworkModule` reads the authored
  `scenery.sh` requirement/replacement; `verifyFrameworkSession` compares the
  selected source digest with the producer's (`VerifyFrameworkProducer`) before
  every build.
- `framework_prepare.go`: `PrepareFramework` snapshots the source and builds the
  producer under `.scenery/framework/bin/<source digest>/<platform>/<executable
  digest>/scenery`; `OwnsFrameworkSelection` decides whether this process may
  publish a receipt.
- `framework_source.go`: `linkedFrameworkDigest`, the source digest linked into
  a prepared producer.

`cmd/scenery/framework.go` implements `scenery framework use|inspect`;
`useAppFramework` resolves, downloads, prepares and optionally rewrites
`go.mod`, and a producer that does not own the result runs the new executable's
own `framework use` to publish its receipt.

`cmd/scenery/watch.go` `runWithWatch` owns one `scenery up` lifetime: session
preparation (worktree ownership), the supervisor, the initial build and the
watch loop that calls `supervisor.RebuildAndRestart`. Its deferred cleanups
stop the runtime. `cmd/scenery/main.go` `upCommandWithTelemetry` dispatches
foreground and detached runs. `cmd/scenery/dev_detach.go` and
`dev_detach_startup.go` implement `up --detach`: the launcher starts a child with
`SCENERY_DEV_DETACHED_CHILD=1`, stdout/stderr in a log file, and a startup pipe
on file descriptor 3 through which the child reports a startup failure.

`cmd/scenery/console.go` `runConsole.Finish` writes the terminal `summary`
event of `-o jsonl`. `internal/generate/dev_runtime_client.ts` is the template
of the generated `dev-runtime.ts`; its committed consumers are under
`internal/compiler/testdata/house/clients/generated/public_api/`.

## Milestones

Milestone 1 changes only the generated client: `status()` distinguishes a
result that is not a `scenery.dev-runtime.status` from a revision mismatch and
attaches the expected and received identities as `details`.

Milestone 2 adds detection and preparation without changing lifecycle:
`build.ReadDesiredFramework` parses the authored selection; a pure decision
function answers whether the running producer is eligible and whether the app
selects another framework; `prepareFrameworkHandoff` runs the `framework use`
preparation with a no-rewrite guard and publishes the new receipt through the
new executable.

Milestone 3 wires the handoff: the watch loop checks before each build, returns
a handoff result that makes the deferred shutdown run, the console writes the
handoff summary, and `upCommandWithTelemetry` or the detached launcher continues
as the new producer.

Milestone 4 updates `docs/local-contract.md`, `docs/agent-guide.md`,
`docs/spec/typescript-client.md`, runs validation and the real-process
acceptance, and closes the plan.

## Plan of Work

Client: in `internal/generate/dev_runtime_client.ts`, read the raw result as
unknown, compare `kind` first and `schema_revision` second, and throw
`DevRuntimeError("protocol", …, { details })` with specific messages. Regenerate
the committed clients with the two generation commands from the root
instructions.

Detection: add `DesiredFramework{Version, Root}` and `ReadDesiredFramework` to
`internal/build/framework_session.go`, reusing the parsing in
`ResolveFrameworkModule`. Add `FrameworkSnapshotDigest(appRoot, root)` returning
the digest named by an app-local snapshot path. In `cmd/scenery`, add
`frameworkHandoffTarget(root)` returning the desired framework when the running
executable is a prepared producer of `root` and the desired selection differs
from `sceneryVersion`/`linkedFrameworkDigest` (exposed as
`build.LinkedFrameworkDigest()`).

Preparation: split `useAppFramework` so a caller can require that `go.mod` stays
byte-identical; the handoff uses that mode and then runs
`<new> framework use --app-root <root> -o json`, checking only its exit status.
A result whose executable is the running one is no handoff.

Execution: `frameworkHandoff` (`cmd/scenery/framework_handoff.go`) is an error
value carrying the new executable and version. The watch loop returns it after
successful preparation; the deferred cleanup stops the runtime and
`console.Finish` writes `ok: true` with `handoff`. `upCommandWithTelemetry` then
calls `continueWithFramework`, which `exec`s the new executable with the same
arguments (foreground) or `up --detach -o json` without the child marker
(detached supervisor). Before dispatch, a foreground or launcher `up` runs
`startupFrameworkHandoff` and `exec`s a prepared new producer directly.

## Idempotence and Recovery

Preparation is content-addressed and reusable; repeating a failed handoff
repeats only the missing work. A handoff that fails before shutdown leaves the
old runtime serving. A new producer that fails to start leaves the worktree
stopped, exactly as a manual restart would; the operator reruns
`scenery up` through the launcher.
